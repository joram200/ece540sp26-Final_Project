 FPGA pins?

● Yes, the MDIO management interface is fully connected to physical FPGA pins.
  Here's the complete picture:

  Pin assignments in rvfpganexys.xdc:

  ┌────────┬──────────┬──────────────┐
  │ Signal │ FPGA Pin │ I/O Standard │
  ├────────┼──────────┼──────────────┤
  │ MDIO   │ A9       │ LVCMOS33     │
  ├────────┼──────────┼──────────────┤
  │ MDC    │ C9       │ LVCMOS33     │
  └────────┴──────────┴──────────────┘

  How the tristate is resolved in rvfpganexys.sv:

  The top-level module uses a Xilinx IOBUF primitive to merge the three-wire
  MDIO interface (mdio_o, mdio_i, mdio_t) from ethernet_top into the single
  bidirectional MDIO pad:

  // rvfpganexys.sv:386-392
  IOBUF mdio_iobuf
    (.IO (MDIO),      // connected to FPGA pin A9
     .I  (mdio_o),    // output from ethernet_top
     .O  (mdio_i),    // input to ethernet_top
     .T  (mdio_t));   // tristate enable from ethernet_top

  And MDC is a simple output port wired directly to ethernet_top.mdio_mdc (pin
  C9).

  So yes — both MDIO data (via IOBUF tristate) and MDC clock are properly
  connected to the physical Ethernet PHY pins on the Nexys A7.

● Adding an XDC pin constraint is a synthesis-transparent change — XDC
  constraints are consumed only during implementation (place & route), not
  synthesis. So:

  - All synthesis runs stay valid — synth_1, axi_ethernet_0_synth_1, and all 5
  sub-IP synthesis runs are unaffected and their DCPs remain cached.
  - Only impl_1 needs to re-run — place_design, route_design, and
  write_bitstream. No painful IP synthesis chain at all.

  Implementation on the Nexys A7 for this design typically takes 10–20 minutes,
  vs. the hour+ the full synthesis chain took last session.

  To re-run just implementation after editing the XDC:

  open_project Hardware.xpr
  reset_run impl_1
  launch_runs impl_1 -to_step write_bitstream -jobs 8
  wait_on_run impl_1

  ---
  Opus's analysis is correct. The bug is real.

  Here's the chain of evidence:

  The data path is a straight passthrough from CPU to adapter:
  VeeR LSU (64-bit AXI) → axi_intercon (no conversion) → eth_cpu → eth_cdc →
  eth_cdc_bus
  Every assignment in axi_intercon.sv for the eth slave port is verbatim:
  - o_eth_wdata = slaves_req[2].w.data (64-bit passthrough)
  - o_eth_wstrb = slaves_req[2].w.strb (8-bit passthrough)

  VeeR EH1 is a proper AXI4 master on a 64-bit bus. For a 32-bit store (SW) to a
   64-bit bus, it lane-aligns per AXI4 spec. For addr[2]=1, it puts data in
  wdata[63:32] and sets wstrb[7:4].

  The adaptation in rvfpganexys.sv ignores this entirely:
  .s_axi_wdata  (eth_cdc_bus.w_data[31:0]),   // always low lane
  .s_axi_wstrb  (eth_cdc_bus.w_strb[3:0]),    // always low lane
  assign eth_cdc_bus.r_data = {32'h0, eth_rdata_narrow};  // always low lane

  Impact on the MAC register map (4-byte stride, so addr[2] alternates every
  register):

  ┌────────┬─────────┬──────┬────────┐
  │ Offset │ addr[2] │ Lane │ Status │
  ├────────┼─────────┼──────┼────────┤
  │ 0x00   │ 0       │ low  │ OK     │
  ├────────┼─────────┼──────┼────────┤
  │ 0x04   │ 1       │ high │ BROKEN │
  ├────────┼─────────┼──────┼────────┤
  │ 0x08   │ 0       │ low  │ OK     │
  ├────────┼─────────┼──────┼────────┤
  │ 0x0C   │ 1       │ high │ BROKEN │
  ├────────┼─────────┼──────┼────────┤
  │ 0x10   │ 0       │ low  │ OK     │
  ├────────┼─────────┼──────┼────────┤
  │ 0x14   │ 1       │ high │ BROKEN │
  └────────┴─────────┴──────┴────────┘

  Exactly half the MAC registers — every odd 4-byte register — are silently
  inaccessible. Writes are dropped (low strobe is all zeros for that access),
  and reads return 0 (CPU samples r_data[63:32] which is hardwired to 32'h0).
