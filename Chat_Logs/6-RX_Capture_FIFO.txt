  ---
  Why Software Cannot Find Packet Data

  Root cause 1 — Wrong interface, no data registers.

  The AXI Ethernet IP (DS759) has no AXI4-Lite register that contains received 
  frame bytes. The entire register map (IS at 0x0C, RCW1 at 0x404, EMMC at
  0x410, etc.) is control/status only. Received frame payload exists exclusively
   on the AXI4-Stream port m_axis_rxd_tdata[31:0].

  main.c treats the MAC like a UART with a data register — that register does
  not exist in this IP.

  Root cause 2 — The stream is hardwired to discard.

  rvfpganexys.sv:455:
  .m_axis_rxd_tready (1'b1),

  m_axis_rxd_tready=1 tells the MAC "I am always ready to consume data." The MAC
   streams every received frame byte out and the design accepts/discards them
  all in hardware. The CPU never sees them — there is no buffer, no FIFO, no
  memory-mapped register that accumulates the stream.

  ethernet_top.sv:70-74 exports m_axis_rxd_tdata/tkeep/tlast/tvalid as output
  ports and m_axis_rxd_tready as an input, so the parent rvfpganexys.sv controls
   draining. Currently it drains everything to /dev/null.

  Root cause 3 — Software only reads interrupt status.

  main.c polls ETH_IS (0x80040000 + 0x0C). When RXCMPLT (bit 2) or RXRJECT (bit
  3) fires, it increments a frame counter and shows it on LEDs. It detects that
  frames arrived but captures none of their bytes.

  ---
  What Must Change to Read Packet Data

  The stream m_axis_rxd_tdata[31:0] needs to land somewhere the CPU can read.
  Two practical options:

  Option A — AXI-Stream capture FIFO (simpler, fits existing architecture)

  Add a small block RAM FIFO in ethernet_top.sv that:
  1. Takes m_axis_rxd_tdata/tvalid/tlast as inputs
  2. Drives m_axis_rxd_tready from the FIFO's prog_full inverse (backpressure)
  3. Exposes two AXI4-Lite read registers: FIFO_DATA (read pops one word) and
  FIFO_STATUS (word count / empty flag)
  4. Maps into the 64-to-32 adapter's address space

  Software would then: wait for RXCMPLT → loop reading FIFO_DATA words until
  FIFO_STATUS says empty → process the frame bytes.

  Option B — AXI DMA (more capable, uses existing IP catalog)

  Wire m_axis_rxd to a Xilinx AXI DMA engine that writes frames to BRAM/DRAM.
  CPU reads from memory. More infrastructure but handles large frames without
  polling.
