  ---
  Analysis

  Historical bug (committed fixes confirmed correct)

  The byte lane adaptation bug was the primary issue: on a 64-bit AXI bus,
  address bit [2] selects which 32-bit half carries the data. The original code
  always used wdata[31:0]/rdata[31:0] regardless of address:

  ┌────────────┬────────┬─────────┬──────────────────────────────────────────┐
  │  Register  │ Offset │ addr[2] │          Effect of original bug          │
  ├────────────┼────────┼─────────┼──────────────────────────────────────────┤
  │ IS         │ 0x0C   │ 1       │ Reads always returned 0                  │
  ├────────────┼────────┼─────────┼──────────────────────────────────────────┤
  │ RCW1       │ 0x404  │ 1       │ Writes sent 0x00000000 → disabled        │
  │            │        │         │ receiver (bit 28 = 0)                    │
  ├────────────┼────────┼─────────┼──────────────────────────────────────────┤
  │ EMMC/SPEED │ 0x410  │ 0       │ Was always correct (low lane)            │
  └────────────┴────────┴─────────┴──────────────────────────────────────────┘

  The axi_lite_64to32 fix is architecturally correct, and the register map is
  confirmed from the XCI:
  - IS at 0x0C ✓, RXCMPLT=bit 2, RXRJECT=bit 3 ✓ (reset value 0x40)
  - RCW1 at 0x404 ✓, RX_ENABLE=bit 28 ✓ (reset value 0x1000FFFF)
  - EMMC at 0x410 ✓, MAC_SPEED_CONF=bits[31:30], reset=0x80000000 (1 Gbps!)

  ---
  Most likely remaining issue: missing MII RX clock constraint

  The MAC IP's internal constraint file (bd_5d9f_0_mac_0_clocks.xdc) line 6:

  set rx_clk [get_clocks -of [get_ports mii_rx_clk]]

  followed by:

  set_input_delay -clock $rx_clk -max 30 [get_ports {mii_rxd[*] mii_rx_er
  mii_rx_dv}]
  set_input_delay -clock $rx_clk -min 10 -add_delay [get_ports {mii_rxd[*]
  mii_rx_er mii_rx_dv}]

  The mii_rx_clk signal is driven by mac_mii_rxc — a toggling FF output from
  rmii_phy_if clocked at 50 MHz (CLKIN), producing 25 MHz. No
  create_generated_clock exists for this signal in rvfpganexys.xdc:

  create_clock -add -name sys_clk_pin ...
  create_clock -add -name tck_dmi ...
  create_clock -add -name eth_rmii_clk -period 20.000 [get_ports { CLKIN }]
  # ← no mii_rx_clk / mac_mii_rxc clock defined

  Without a defined clock on mii_rx_clk, $rx_clk is empty, the set_input_delay
  constraints fail silently, and the entire MII RX data path (mii_rxd,
  mii_rx_dv, mii_rx_er) is unconstrained. Vivado may also fail to route
  mac_mii_rxc through a BUFG (required for correct clock distribution to the
  MAC's internal FFs), causing clock skew that corrupts received nibbles. The
  MAC then never asserts RXCMPLT or RXRJECT in IS — which matches the observed
  symptom (LED never toggles).

  Fix: Add to rvfpganexys.xdc:

  create_generated_clock -name mii_rx_clk \
      -source [get_ports CLKIN] \
      -divide_by 2 \
      [get_pins u_ethernet_top/u_rmii_phy_if/mac_mii_rxc_reg/Q]

  This gives Vivado a 40 ns (25 MHz) clock to work with, allows the MAC IP's
  set_input_delay constraints to apply to mii_rxd/mii_rx_dv/mii_rx_er, and
  ensures the clock is routed through a BUFG.

  ---
  Secondary issue: MAC boots in 1 Gbps mode

  EMMC reset value is 0x80000000 → bits[31:30]=10 = 1 Gbps. The rmii_phy_if
  generates mac_mii_rxc at 25 MHz (100M mode), so the MAC's internal framing is
  wrong until the firmware writes ETH_SPEED. The ETH_SPEED = (1u << 30) write
  (0x40000000 = 100 Mbps) hits the correct low lane (addr[2]=0 for 0x410) and
  was always working — but it was only added in the "Set LAN speed" commit. If
  this write is delayed (e.g., firmware initializes slowly) and a packet arrives
   before it completes the hard register access, that packet is dropped. This is
   a transient race on startup, not a persistent failure.

  ---
  Summary: The byte lane and speed bugs are fixed. The persistent failure is
  almost certainly the missing create_generated_clock for mac_mii_rxc →
  mii_rx_clk, leaving the MII receive data path unconstrained and likely routing
   without a BUFG.
